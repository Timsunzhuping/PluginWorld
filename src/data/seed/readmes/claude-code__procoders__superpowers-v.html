Compound V

by ProCoders

Give Claude Code a senior engineer's habits: it interviews the client first and proves the work before it says done.

The loop that gets you blamed

You prompt, Claude builds, you click through the happy path, it works, you ship. A week later the client calls: the session didn't end on logout, someone booked 24 fake appointments, a mangled cookie returns a server error, a customer's name is rejected, and staff still can't change a price without you. The client doesn't blame Claude. They blame you.

We measured that loop. Plain Claude Code got the full requirements, and a developer (an agent playing a busy one) tested it the way a busy developer does and sent fixes until they were happy to hand over ($2.27 of Claude, two rounds). They found one bug. Blind judges then found every defect above in the same build. Your own happy-path check can't see them, because you check what you built, not what you forgot.

Compound V works both ends, and the middle

  • Before the code: the questions nobody asked. The brainstorm interviews you (or your client) one question at a time: who runs it day to day, what the operator changes without a developer, the country's privacy rules, every form and who could abuse it, the edge cases on purpose. In an earlier experiment, a plain build given just these answers nearly doubled the edge cases it handled (37 → 63).
  • In the middle: it picks up a live project. On existing code the builder reads before it writes. It maps every rule, every operation and every guard the change touches, so a new feature goes through the existing validation instead of beside it. Added to a running app, recurring bookings scored 85 and 93. Plain Claude Code's attempt made an existing staff delete crash, and was capped in 5 of 6 judgements.
  • At handover: acceptance you can't fake. The project's tests, a real browser submitting real forms, an independent reviewer attacking an isolated copy (logout, other users' data, abuse from many networks, production start with example secrets), and a look at its own screenshots against the project's DESIGN.md. Each check is a signed receipt bound to the exact code. Without them Claude can't report "done": if it tries to stop, a hook refuses once and names what is missing, and the run is recorded as incomplete.

What the score means. The judges check every requirement by running it, then try to break it, and score requirements, correctness under their probes, product thinking, security, code and operability. Around 60, the happy path works and holes like the ones above are open. Above 80, the judges found no critical defect and few gaps. One critical defect caps any build at 50. It's a rubric, not a production outcome, but the points between 60 and 80 are the defects listed in this table.

It isn't one lucky app. On a team-expenses app (TypeScript, Fastify, Drizzle, Zod) plain Claude Code scored 52 (59 with the owner's answers) and Compound V 80 before critical-defect caps (52, 49.5 and 70 after them; v4's one cap was a type-check failure, now a rule), with ~82 edge cases handled against 44–52.

Is ~$11 worth it? Compare it with one bounced delivery.

Is it for you?

Yes, if you build things other people will use: client work, internal tools, SaaS features, anything with logins, personal data, money or a real operator behind it. Those are the places where one missed case costs more than the run.

No, for prototypes, spikes, throwaway scripts or a tight edit-run loop. There, plain Claude Code is the right tool, and Compound V gets out of the way: typos, copy and config changes go straight to a light check.

How it works

you ─▶ brainstorm ─▶ build ─▶ verify ─▶ done (only if every receipt is green)
       questions     one builder:         tests · real browser ·
       one at a      research → plan →    second-model review ·
       time          code + tests         scope check
  1. Brainstorm. One question per message: who uses it, the data lifecycle (what the operator changes without a developer), jurisdiction and privacy, every form and who can abuse it, operations, and the edge cases on purpose. If it's a new project with a UI, one more question: the name, contacts and look. You approve a written spec.
  2. Build. One fresh builder agent researches the domain (sourced requirements, not vibes), reads the code it will touch and maps every rule, operation and guard it must respect, checks current library APIs, and then writes a plan with an acceptance table and builds it with tests. For UI it keeps a DESIGN.md (Google's format) and shared components instead of copy-paste, and looks at its own screenshots before calling it finished.
  3. Verify. The project's tests, a real browser submitting real forms, a scope check, and an independent reviewer (Codex or a fresh Claude) that attacks an isolated copy with probes that found real bugs before: boundaries, cross-user access, session replay, abuse from rotating networks, production start with example secrets. It gets at most one fix round.

Each check writes a signed receipt bound to the exact working tree. Edit a file and the receipt goes stale. The outcome is verified, incomplete or failed, and Claude can't talk its way to "done": the Stop hook refuses once, with the reason.

Install

claude plugin marketplace add procoders/superpowers-v
claude plugin install compound-v@procoders

Then, once per project:

/compound-v:init

Needs Claude Code, git with at least one commit, and Python 3.9+. Optional: codex as the second-model reviewer (otherwise a fresh Claude Opus reviews), and Playwright in web projects for the browser check. Init shows every change as a diff and writes nothing without your yes.

Commands

You rarely type them: in a set-up project a hook reads each request and sends it to brainstorm or straight to a light verify.

Command When
/compound-v:init Once per project, and again after installing Codex or Playwright
/compound-v:brainstorm Anything bigger than a typo: a feature, a page, a flow, a new app
/compound-v:verify After any change, to get it to verified
/compound-v:onboard Build a citation-checked knowledge base of an existing repo (--refresh when stale)
/compound-v:pr-review Deep review of a PR, a commit range or a local diff. Never edits code

plan, build and design are the builder's own playbook; brainstorm hands off to them. Its own records live in docs/compound-v/.

Light and full

Run For Must pass
light typo, copy, config tests, scope, plus the browser when a page changed
full features tests, browser, review, scope

The tier follows the diff's content, not the file names. A "small fix" that touches auth, sessions, payments, personal data or a new endpoint becomes a full run on its own.

Coming from v3

v4 is a new plugin id (compound-v). It doesn't need Superpowers and has no orchestration engine: Claude Code orchestrates itself, and Compound V brings the questions, the checklists and the proof. The /v:… commands are gone, along with dispatch, epic, resume, status, lessons and remember. CHANGELOG.md says why. v3 stays installable as superpowers-v@procoders from the v3 branch; finish open v3 runs there. If both brainstorms fire, /compound-v:init offers to switch Superpowers off for the project. The Compound V Academy teaches the v3 pipeline; the ideas carry over.
