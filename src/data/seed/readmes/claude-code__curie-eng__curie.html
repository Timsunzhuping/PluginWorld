Curie

Turn agents into co-workers. Run them in your infrastructure. Start with a Software Factory co-worker

Curie brings agents into the workspaces your team already uses. Delegate work, follow progress, approve restricted actions, and inspect the result. The platform is Apache-2.0 and runs in your infrastructure, with shared memory facilities, model configuration, and cost visibility.

Start with a Software Factory co-worker that turns delegated GitHub, GitLab or Jira Cloud issues into reviewed pull requests or merge requests, or an SRE co-worker that investigates Kubernetes workloads from Slack. Then convert your existing agents into a co-worker with supported skills and tools onto the same platform.

Quickstart

The software factory and SRE co-workers below run on local kind clusters. They use the same platform you can later install on your own Kubernetes infrastructure.

You need Docker running, kind, kubectl, Helm, and an Anthropic or OpenRouter model credential. Use a Bash terminal and keep the variables in that session. Allow enough Docker memory and disk for Curie and the SRE observability stack. The factory prerequisites list supported machines and tools.

Install the released CLI:

curl -fsSL https://raw.githubusercontent.com/curie-eng/curie/main/get-curie.sh | bash
if [ -w /usr/local/bin ]; then
  export PATH="/usr/local/bin:$PATH"
else
  export PATH="$HOME/.local/bin:$PATH"
fi
hash -r
curie --version

Enter your model credential without echoing it, then select a model available through that provider. For OpenRouter, use its full provider/model identifier.

read -rsp 'Model credential: ' CURIE_CREDENTIALS
printf '\n'
export CURIE_CREDENTIALS
read -rp 'Model ID: ' CURIE_MODEL
export CURIE_MODEL

GitHub

Create a GitHub repository with an initial commit, or use a small existing repository. Write a bounded issue with clear acceptance criteria.

1. Start the local factory setup. A dedicated kubeconfig keeps this trial separate from your other clusters.

read -rp 'Repository (owner/name): ' CURIE_FACTORY_REPO
CURIE_FACTORY_CLUSTER="curie-factory-$(date +%s)"
CURIE_FACTORY_KUBECONFIG="$(mktemp)"
KUBECONFIG="$CURIE_FACTORY_KUBECONFIG" curie factory quickstart \
  --repo "$CURIE_FACTORY_REPO" --kind-name "$CURIE_FACTORY_CLUSTER" \
  --model "$CURIE_MODEL"

The command creates a local kind cluster, installs Curie, and prints a GitHub App registration link. Open that link, create the App, generate its private key, and install it on the selected repository. Note the App ID and the absolute path of the downloaded key file.

2. Complete the setup with your App.

read -rp 'GitHub App ID: ' CURIE_FACTORY_APP_ID
read -rp 'Private key file (absolute path): ' CURIE_FACTORY_APP_KEY
KUBECONFIG="$CURIE_FACTORY_KUBECONFIG" curie factory quickstart \
  --repo "$CURIE_FACTORY_REPO" \
  --kind-name "$CURIE_FACTORY_CLUSTER" \
  --model "$CURIE_MODEL" \
  --app-id "$CURIE_FACTORY_APP_ID" \
  --private-key-file "$CURIE_FACTORY_APP_KEY"

3. Delegate the issue. Add the curie-factory label in GitHub. The person adding it needs write or admin access to the repository.

The issue status comment shows progress through planning, implementation, review, publication, and CI. Inspect the resulting PR and its verification information. A failed or ambiguous task reports its reason. Mention the configured App in a new comment to request a revision.

The trial enables automatic initial PR publication. Curie does not merge the PR; your team accepts the result. Production agents default to human publication approval. Configure implementation and reviewer models explicitly, then use usage estimates and your accepted outcomes to evaluate costs.

See the complete factory quickstart for checkpoints, troubleshooting, timing and cost guidance, and cleanup. The factory overview explains review and CI limits.

When finished with the trial, delete its local cluster:

kind delete cluster --name "$CURIE_FACTORY_CLUSTER"

SRE co-worker on your laptop

Create a Slack app with Socket Mode and interactivity, install it in your workspace, and invite it to a channel. Collect its app-level token, bot token, channel ID, and the Slack user ID of an approver. Follow Slack app setup using the app manifest.

1. Create a local cluster and select your Slack channel.

CURIE_SRE_CLUSTER="curie-sre-$(date +%s)"
CURIE_SRE_KUBECONFIG="$(mktemp)"
kind create cluster --name "$CURIE_SRE_CLUSTER" --kubeconfig "$CURIE_SRE_KUBECONFIG"
read -rp 'Slack channel ID: ' CURIE_SRE_CHANNEL
read -rp 'Approver Slack user ID: ' CURIE_SRE_APPROVER

2. Install the co-worker and its observability stack.

KUBECONFIG="$CURIE_SRE_KUBECONFIG" curie example sre-bot install \
  --context "kind-$CURIE_SRE_CLUSTER" --observability \
  --slack-channel "$CURIE_SRE_CHANNEL" --approvers "$CURIE_SRE_APPROVER"

The installer provisions Curie, Grafana, Loki, Tempo, and Prometheus, creates the Kubernetes connector identity, binds the approval route, and deploys the SRE bundle. The exported model credential from the quickstart is required for real replies.

3. Connect Slack.

read -rsp 'Slack app-level token: ' SLACK_APP_TOKEN
printf '\n'
read -rsp 'Slack bot token: ' SLACK_BOT_TOKEN
printf '\n'
export SLACK_APP_TOKEN SLACK_BOT_TOKEN
KUBECONFIG="$CURIE_SRE_KUBECONFIG" curie cluster comms \
  --context "kind-$CURIE_SRE_CLUSTER" --slack

4. Ask it to investigate. Mention the bot in the bound Slack channel:

Which workloads in this cluster are unhealthy? Show the evidence and suggest a next step.

Read-only Kubernetes tools run immediately. Configured mutations request a fresh human approval; the default write permissions are limited to the disposable sre-demo namespace. An approval does not expand those permissions.

Use a dedicated Slack app for this trial: one app must connect to only one Curie release. GitHub is optional for triage; repository work needs the separate allowlist and GitHub App configuration in the SRE guide. That guide also covers installation details, permission boundaries, and demo scenarios.

When finished with the trial, delete its local cluster:

kind delete cluster --name "$CURIE_SRE_CLUSTER"

Make your existing agent a co-worker

Keep your agent's useful instructions and tools. Curie provides workspace interaction, deployment, supervision, and operational controls around a supported bundle.

Watch how Curie turns an existing agent into a co-worker, then follow the steps below to adapt your own agent.

  1. Adapt the package. Put instructions into skills and declare tools through MCP. Existing deterministic code can remain behind a tool wrapper.
  2. Test a representative task locally. Check tool discovery, run your agent with a real model, and inspect which tools it used.
  3. Connect a workspace. Deploy the bundle and bind its Slack channel.
  4. Configure shared controls. Choose approval routes, memory scope, models, and budgets appropriate to the job.

For an existing directory, start by scaffolding the supported bundle alongside its files:

curie init --adopt ./my-existing-agent

Port the instructions and tool declarations using the adoption guide, then test them:

cd my-existing-agent
curie skill check --json
curie skill up --model "$CURIE_MODEL"
curie skill message "Run a representative task using your tools."
curie skill down

Scaffolding preserves existing files; adapting the agent's behavior is manual. The supported path reuses skills and tools in a Curie bundle. Attaching an arbitrary agent runtime unchanged requires a separate integration.

Continue with bringing your agent, connecting Slack, and administering co-workers.

Run it in your infrastructure

Both examples and your supported custom agents use the same platform. Administrators control deployment, credentials, approvals, model settings, memory, and bounded runs. Configured model providers and workspace services receive the integration data they need.

  1. Production operations: installation, backing stores, egress, upgrades, and operational limits.
  2. Administrator guide: approvals, memory, models, budgets, inspection, and stop controls.
  3. Factory outcome measurement: accepted work, estimated spend, and human review effort.
  4. Capabilities: supported integrations and their limits.
  5. Documentation: guides and technical references.

Plain curie cluster up infers Anthropic or OpenRouter egress from an unambiguous credential prefix. Before Helm runs, a NotFound GET for the rendered gVisor RuntimeClass makes Curie apply security.gvisor.mode=off, unless the chart creates that RuntimeClass. A Forbidden GET retains one retry only after admission reports RuntimeClass "gvisor" not found. Other read errors and admission refusals stay closed. Each inference is printed with the equivalent override. Ambiguous credential shapes still need an explicit --allow-egress-host, and explicit values that contradict detected facts are errors.

For the skill, local, and cluster tiers, see the CLI target guide and bundle quickstart. The architecture reference covers local to production parity and what is built vs deferred.
